측면 장착 S300/RB5 카메라 순회·수확 시험
========================================

실행
----
cd /root/farmily_tomato
bash nvidia-sim/run_s300_harvest.sh camera-patrol

현재 기본값:
  - 레일 입구에서 시작하는 측면 장착 RB5 + 실제 리프트 받침대
  - 원본 농장 시각 환경과 기존 활성 식물/장애물 정책
  - 실제 장착 카메라의 정면 RGB-D + 보이는 SIM-GT 분류
  - 레일 왼쪽의 가장 가까운 지정 거터 한쪽만 작업
  - 보통 0.15m씩 전진, 한 명령은 최대 0.20m
  - 서로 다른 송이 6개에서 기존 기준의 실제 분리 증거 확보가 목표
  - 유한한 최대 80개 이동/스캔/수확 결정
  - 실제 저장 구간이 생기면 웹 재생 이력에 자동 등록

옵션 예:
bash nvidia-sim/run_s300_harvest.sh camera-patrol \
  --patrol-step-m 0.10 --patrol-max-decisions 100 --patrol-goal-trusses 6

실행 결과 폴더를 지정하려면 S300_ISAAC_OUTPUT 환경 변수를 사용한다.
기존 폴더를 덮어쓰지 않으므로 매번 새 경로를 지정해야 한다.
장면 변경은 S300_ISAAC_ASSEMBLY, 실제 농장 inventory 변경은
S300_PATROL_INVENTORY 환경 변수로 지정한다. 모델·inventory가 서로 맞아야 한다.

현재 기본 자산:
  /root/docker_share/mujoko_debugging_data/20261023_side_mount_camera_patrol/assembly_side_entry
  /root/docker_share/mujoko_debugging_data/20261023_side_mount_camera_patrol/full_farm_inventory.json
real-lift 실행도 같은 측면 장착 assembly_side_entry를 기본으로 사용한다.
S300_ISAAC_ASSEMBLY를 지정하면 해당 실행의 기본 장면 대신 사용한다.
현재 실행 프로필:
  nvidia-sim/harvest_s300/side_camera_patrol_arguments.json
  Isaac Sim6.1 native PhysX CPU60Hz, 카메라2Hz, 기존1mm 관통 검사.
  이 프로필의 결과는 Newton GPU 성능 검증 결과가 아니다.

화면 연결 사전검사
----------------
명령 하나로 실행할 때 benchmark_motion은 native Kit를 띄우기 전에
현재 DISPLAY에 xdpyinfo를 보내 실제 X 프로토콜 응답을 확인한다.
각 확인은 최대2초다. 소켓 파일이 있거나 프록시에 연결된다는 이유만으로
정상 화면으로 인정하지 않는다.

상속된 DISPLAY가 실패하면 기존 :0이 실제 응답하는 경우에만 :0을 사용한다.
선택과 사유는 터미널과 각 시험의 NAME_display_precheck.json에 기록한다.
둘 다 사용할 수 없으면 native 프로세스를 시작하기 전에 중단한다.
별도 X 서버를 만들거나 GPU를 초기화하지 않으며 물리 설정도 바꾸지 않는다.
physics-only도 Kit를 초기화하므로 같은 검사를 적용한다.

화면을 명시적으로 고정하려면:
S300_NATIVE_DISPLAY=:0 bash nvidia-sim/run_s300_harvest.sh camera-patrol

S300_NATIVE_DISPLAY가 지정되면 해당 화면만 검증한다.
실패했을 때 다른 화면으로 조용히 바꾸지 않고 실행 전에 중단한다.
X 응답 확인은 Vulkan/GPU 장치 생성 성공을 보증하는 검사가 아니다.

이동·수확 결정
------------
실제 카메라 촬영 → 익은 열매/유효 depth가 있는 송이를 대기열에 저장
→ 관측 위치와 실제 카메라/그리퍼 장착 보정으로 정차 위치 제안
→ 최대0.20m 물리 레일 이동 → 재촬영 → 지정 송이의 기존 수확 계획 검사
→ 실제 수확1회 → 재촬영 → 남은 집단 또는 다음 대기 송이 판단.

inventory는 정확한 식물/송이 소속과 거터 쪽 분류에 사용한다.
진입 목표의 위치는 보이는 depth에서 계산하며 숨겨진 과실 중심을 쓰지 않는다.
실제 IK·전체 경로·환경 충돌 검사와 물리 실행은 기존 코드를 재사용한다.

카메라에서 보인 송이는 시야 밖으로 나가도 대기열에서 사라지지 않는다.
최소2개 익은 열매가 모인 집단이 대상이며, 한두 개의 시야 픽셀만 보이거나
유효 depth가 없는 물체는 사유를 남긴다. 유한 탐색 실패를 불가능으로 기록하지 않는다.
한 정차 위치의 유한 계획들이 모두 실패한 경우 최대3개 서로 다른 전진 위치를
검토하며, 거부 사유와 원자료를 보존한다. 실제 물리 중단은 이 계획 재시험과 구분한다.

활성 식물에 아직 관측된 작업 대상이 있으면 다른 식물로 바꾸기 전에 우선 처리한다.
현재 촬영에서 보이는 집단의 작업 기준 위치가 현재 정차점으로부터 ±0.20m 이내면,
그 자리에서 팔만 사용해 기존 진입 계획을 시도하는 제안을 할 수 있다.
visible_service_offset_proposal_m은 이 제안 범위이며 정차·충돌 허용 오차가 아니다.
기존60mm 작업 정차 기준, 실제 레일 도착2mm 검사와1mm 관통 검사는 그대로 적용된다.
제안은 실제 IK·전체 경로 검사·물리 실행을 통과해야 하며, 통과한 것으로 가정하지 않는다.
50mm 전진 재시험은 고정된 절대 레일 위치를 사용한다. 새 depth의 작은 위치 흔들림이
전진 목표를 계속 움직이게 하지 않는다.

촬영 완료와 실제 수확 동작 구분
----------------------------
native가 completed=true로 끝나도 촬영만 실행하고 진입 계획이 모두 거절됐다면
실제 벨트 수확 횟수는0이다. completed_native_cycles의 실제 완료 기록과
selected_cycle_evidence의 실제 벨트 단계로 확인하며, harvest라는 결정 이름만으로
물리 수확을1회 했다고 세지 않는다. 이전 순회의 횟수도 같은 실제 증거로 다시 계산한다.

실제 촬영 뒤 모든 유한 계획이 거절된 경우, 새로 측정하고 검증한 마지막 체크포인트를
먼저 보존한다. 그 새 상태에서 50mm 전진하고 다시 촬영하는 제안을 한다.
촬영 중 실제 physics가 실행됐다는 사실과 수확 팔 동작을 실행하지 않았다는 사실을
native_observation_executed=true, harvest_motion_executed=false로 따로 기록한다.
이 처리는 실제 물리 중단이나 증거가 없는 일반 오류의 재시험 허가가 아니다.

OMPL의 정확한 LimitReached: wall_time_budget는 입력 plan/scene 해시와
source_files_unchanged=true, physics_steps=0, 유한 예산·검사 횟수가 확인될 때만
알려진 유한 계획 예산 소진으로 분류한다. 의미는 reachability=unknown이며
path_clear=false, impossible=false이다. 안전한 경로를 찾았다는 뜻이 아니고,
남은 탐색을 평가하지 못했다는 뜻이다. 다른 예외·해시 불일치·불명확한 실패를
이 경우로 넓혀 처리하지 않는다.

이전 대기열 기록에 새 제안 범위 설정이 없으면 새 기본값을 읽되,
재개 증거의 new_explicit_queue_proposal_defaults에 추가된 정책 기본값을 기록한다.
이전 기록과 해시는 보존하며, 과거 시험이 새 정책으로 수행됐다고 바꾸지 않는다.

6송이의 의미
-----------
숫자6은 열매6개, 촬영6회, 움직임6회가 아니다.
기존 measured_harvested_trusses 판정으로, 완료된 실제 벨트 수확 구간 중
선택한 열매의 새 native 분리 이벤트가 있는 서로 다른 식물/송이를 센다.
같은 송이에서 여러 열매가 떨어져도 송이 수는1이다.
송이의 열매를 전부 땄다거나 수거함에 안전하게 모았다는 뜻은 아니다.
목표 미달이면 goal_reached=false를 유지한다.
training_eligible=false, harvest_success=null을 유지한다.

측정 상태 연속성 및 제한된 식물 재활성화
-----------------------------------
다음 구간은 검증된 마지막 실제 체크포인트에서 시작한다.
로봇·리프트·레일의 측정 상태와 검증된 제어 목표를 구분해서 보존한다.
활성 식물을 바꾸면 이전 붙어 있는 식물은 측정 변형 상태에서 정적으로 동결된다.
이것은 주변 모든 식물을 계속 탄성 계산하는 방식과 다르며 native solver는 다시 시작한다.

처음 활성화했던 식물이 레일 뒤쪽 작업 대상보다 앞에 있을 수 있다.
그 식물을 잠시 동결했다가 다시 사용할 때, 기존 native 분리가0개인 경우만
검증된 예전 USD/skin/관절 q/preload로 되돌려 활성화할 수 있다.
기존 동결 형상이 원래 측정 형상과 일치해야 하며, native의 실제 위치/회전/q 검사도
통과해야 한다. 동결 기간 붙어 있던 몸체의 속도는 정적 근사에 따라0으로 복원한다.
다른 식물에서 떨어져 움직이고 있던 열매는 현재 체크포인트의 상태를 유지한다.
자기 열매가 이미 떨어진 식물의 일반적인 재활성화는 지원하지 않으며 명시적으로 막는다.
떨어진 열매를 다시 붙이거나 새 과실로 재생성하지 않는다.

native 초기화 중 관절이 끊어지면 기존 초기화 실패 검사가 중단시킨다.
이 실패를 지우거나 이전 체크포인트로 돌아가 계속 성공한 것으로 처리하지 않는다.

사용하지 않은 새 창의 초기화 진단
-----------------------------
startup_preflight는 아직 수확에 사용하지 않은 새 활성 창의 별도 검사다.
이 진단에서만 physics-only를 사용하여 불필요한 카메라·렌더링 준비를 생략한다.
실제 순회·수확은 계속 렌더링된 실제 장착 RGB-D/GT 촬영 경로를 사용한다.
startup 통과를 실제 촬영이나 수확 실적으로 세지 않으며, 캐시도 정확한 모델·입력·
부모 체크포인트·실행 환경이 같은 독립 진단에만 재사용한다.

초기 A/B 증거:
  /root/docker_share/mujoko_debugging_data/20261023_side_mount_camera_patrol/startup_physics_only_ab_validation.json
해당 비교는 같은 모델/물리 제어에서 렌더링 진단과 physics-only 진단이 모두
첫1스텝(1/60초)에 같은 관통 판정으로 중단되었으며 저장된 위치/명령이 정확히 같았다.
이는 그 초기 차단 사례의 비교 근거이며, 전체 수확 시간이나 모든 장면의 물리 동등성을
검증한 결과로 확대 해석하지 않는다.

같은 원본 식물의 공통 초기화 오류에 대한 운영 격리
----------------------------------------------
새 창이 식물 전체(full plant)를 사용하고, 실제 native 초기화/idle 진단에서
그 초기 모델의 물리 유효성 위반이 확인되면 같은 원본 식물의 다른 송이를
하나씩 다시 초기화하는 대신 이번 순회의 작업 대상에서 운영상 보류할 수 있다.
이는 로봇이 진입하기 전의 공통 입력 문제를 반복하지 않기 위한 조치다.

이 조치는 아래 증거가 함께 있을 때만 적용한다.
  - 아직 사용하지 않은 새 창이며 기존 받아들인 부모 상태가 바뀌지 않았음
  - native 초기화가 실제 관측되었고 초기화/idle 물리 오류가 명확히 확인됨
  - 해당 진단의 상태를 순회의 실제 상태로 받아들이지 않았음
  - 실제 순회 로봇 동작이나 수확은 아직 실행하지 않았음
  - plant-dynamics=full이며 타깃별 별도 식물 변형 옵션을 사용하지 않았음

시간 초과·증거 부족·일반 소프트웨어 오류나 타깃별 IK/진입 실패만으로는
같은 식물 전체를 격리하지 않는다. 충돌체·관통 기준·물성은 바꾸지 않는다.
다른 모델이나 별도 타깃 변형까지 같은 실패로 간주하지 않는다.

보류된 송이의 상태는 not_attempted_shared_invalid_initial_model이다.
뜻은 "공통 초기 모델이 유효하지 않아 이 송이는 아직 시도하지 않음"이다.
그 송이마다 독립 수확 시험에 실패했다거나 수확이 불가능하다는 뜻이 아니다.
기록에는 other_targets_individually_tested=false, reachability=unknown,
impossible=false와 실제 검사한 타깃·startup 증거·부모 상태를 함께 보존한다.
이 상태는 수확 성공, 실제 수확 실패 횟수 또는 절대 불가능 레이블에 더하지 않는다.

카메라가 이미 본 송이는 대기열에서 지우지 않는다. 같은 원본 식물의 송이가
나중에 추가로 보이면 관측을 저장하고 같은 보류 사유를 연결한다.
camera_patrol_queue.json의 plant_quarantines와 evidence_history는 저장·재개 시에도
보존한다. 새 실제 native 분리 증거가 생기면 그 사실은 별도로 유지한다.
보류를 임의로 지우지 않으며, 식물을 새 초기 상태로 재생성해 성공으로 기록하지 않는다.

2026-10-23 이 설명을 추가한 시점의 실제 수확 집계는0/6이며 목표는 미완료다.
최신 실행 상태와 실제 수확 수는 결과 폴더의 index.html/final_status.json 및
camera_campaign_report.html/json을 확인한다. 격리·이동·촬영은 이 숫자를 올리지 않는다.

기록과 재생
----------
  camera_patrol.json       전체 결정/실행/실패/서로 다른 송이 집계
  camera_patrol_queue.json 보인 송이, 관측 위치, 남은 열매, 유한 실패 대기열
  replay_segments.json     실제 저장 상태가 존재하는 구간의 웹 재생용 원본 목록
  trials/                 실제 states.npz, summary, 접촉·분리·카메라 기록
  startup_preflight/      새 활성 창의 별도 초기화/idle 검사; 수확 실적에 포함하지 않음
  windows/                각 활성 식물 전환의 검증된 새 불변 USD 자산

웹에서는 실제 저장 상태를 재생한다. 재생 중 다시 물리 계산하는 것이 아니다.
자연스러운 다음 구간 전환은 같은 유효 기록의 경계에서만 적용하며,
독립 재시험이나 중단 구간을 하나의 성공 동작으로 숨기지 않는다.

웹 재생 자동 등록
----------------
위 camera-patrol 명령 하나로 순회 실행과 웹 등록 작업이 함께 시작된다.
등록 작업은 실제 저장된 상태를 읽으며 추가 물리 실행을 하지 않는다.
완료된 구간은 실제 저장 자료를 확인한 뒤 등록하고, 중단·부분 기록은
별도 진단 이력으로 구분한다. 웹 등록 여부가 수확 성공 수를 바꾸지는 않는다.
목표6송이의 실제 달성 여부는 camera_patrol.json의 native 증거 집계를 확인한다.

기본 웹 이력 이름은 camera_patrol_YYYYMMDD_HHMMSS이다.
출력 폴더와 웹 이력 이름을 고정하려면 매번 새로운 이름을 지정한다:

S300_ISAAC_OUTPUT=/root/docker_share/mujoko_debugging_data/my_new_camera_patrol \
S300_REPLAY_COLLECTION=my_new_camera_patrol \
  bash nvidia-sim/run_s300_harvest.sh camera-patrol

이 예의 웹 주소:
  http://lab.farmily.ai:8090/gripper-design/harvest-replay/?collection=my_new_camera_patrol

실행 출력 폴더를 OUTPUT이라고 할 때 웹 등록 로그는 OUTPUT_web.log에,
등록 상태·구간별 로그·검증 결과는 형제 폴더 OUTPUT_web_publication/에 저장된다.
후자에는 videos.json과 videos.md 영상 목록도 기록된다.
등록 작업이 실행 결과 폴더를 미리 만들거나 원본 시험 기록을 덮어쓰지는 않는다.
이미 다른 시험에 속한 이력 이름은 새 이름으로 바꿔야 한다.

자동 등록을 끄고 실제 순회만 실행하려면:
S300_PUBLISH_REPLAY=0 bash nvidia-sim/run_s300_harvest.sh camera-patrol

이미 저장된 순회 결과를 따로 등록하거나 등록을 다시 이어가려면:
nvidia-sim/.asset-venv/bin/python gripper-design/harvest-replay/publish_patrol.py \
  --campaign /root/docker_share/mujoko_debugging_data/my_new_camera_patrol \
  --collection my_new_camera_patrol --watch

--watch는 새 실제 기록을 기다리며 최대8시간 동작한다.
현재 저장 자료만 한 번 등록하려면 --watch 대신 --once를 사용한다.
같은 등록 출력에는 한 작업자만 실행된다. 다른 시험을 같은 이력으로 합치지 않는다.

중간에 멈춘 조정기만 이어 실행할 때
-------------------------------
--patrol-prior-campaign와 --initial-native-checkpoint를 함께 사용한다.
S300_ISAAC_ASSEMBLY는 이전 보고서의 accepted_assembly와 같아야 한다.
체크포인트는 accepted_checkpoint의 정확한 최종 측정 상태여야 한다.
이전 대기열/실적/코드·입력 해시와 모순되면 재개를 거절한다.
실제 물리가 중단된 시험에서 더 오래된 성공 체크포인트를 골라 재개할 수는 없다.

이전 조정기가 위의 알려진 예산 소진을 일반 오류로 잘못 분류해 멈춘 경우에는
그 오류 문구와 마지막 실제 결과를 엄격하게 대조한다. native가 정상 완료됐고,
초기 물리 유효성·실제 자기충돌 검사가 통과했으며 실제 수확 횟수가0이고,
새 분류기가 저장된 모든 계획을 유한 실패로 증명하는 경우만 제한적으로 이어간다.
저장 summary·입력·모델·시간·받아들인 최신 체크포인트가 정확히 같아야 한다.
처음에는 실제 카메라로 다시 확인하고, 마지막 한 번의 계획 실패에 대해서만
한 번의 전진 재시험을 예약한다. 과거 실패를 모두 다시 적용하지 않는다.
원본 보고서·대기열·해시는 보존하고 새 재개 기록에 분류 변경 근거를 연결한다.
관통·충돌 등 실제 물리 중단, 불완전한 실행, 일반 소프트웨어 오류에는 적용하지 않는다.

같은 시각에 추가된 최종 계획 기록
------------------------------
촬영이 끝난 시각과 그 뒤 physics 없이 계획만 검사한 시각이 같을 수 있다.
이때 completed_final_checkpoint가 고른 cycle_checkpoints/000에는 촬영 완료 기록만,
최종 route_checkpoint에는 그 뒤 거절된 계획 기록도 있을 수 있다.

둘의 시각·모델·출처·제어 목표·분리 이벤트 등 sequence 외 메타데이터가 같고,
body 경로/pose/velocity, robot 이름/q/qvel, plant 이름/q/qvel, preload 등
10개 native 배열의 키·dtype·shape·모든 바이트가 정확히 같아야만 최종 계획 기록을 읽는다.
기존 체크포인트의 완료 조건과 SHA 검증도 그대로 통과해야 하며,
최종 sequence는 summary 및 저장 truss_sequence.json과 완전히 일치해야 한다.
최종 내용은 촬영 후 거절된 계획뿐이어야 한다.

검증에 통과해도 실제 재개 경로는 원래 받아들인 cycle 체크포인트 그대로다.
최종 route_checkpoint로 물리 상태를 교체하거나 q/속도/변형을 초기화하지 않는다.
배열·시간·제어·분리 상태가 하나라도 달라지면 이 예외를 허용하지 않는다.
