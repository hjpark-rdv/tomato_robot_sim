# 6변수 진입 동작 소규모 시험 (2026-09-21)

후속 64환경/64후보 실측은 13분 35초로 완료했다. 최신 결과와 대표 영상 기능은
[DATASET_REPRESENTATIVE_VIDEOS.md](DATASET_REPRESENTATIVE_VIDEOS.md)를 참고한다.
아래 수치는 먼저 완료한 4환경 소규모 시험 당시 기록이다.

4개 GPU 환경에서 서로 다른 Sobol 동작 8개를 끝까지 실행했다. 시간 제한으로 자르지 않았다.
이번 턴의 범위는 작은 기능·시간 시험이며, 2,048개 탐색이나 RL 구현 완료를 뜻하지 않는다.

## 실행 결과

- 전체 실행: **269.06초 (4분 29초)**. 대화 중단으로 종료된 앞선 두 실행은 제외했다.
- 초기 실행/종료 등: 34.81초. 내부 장면 초기화 17.55초는 여기에 포함된다.
- 계획 대기·리셋·물리·판정·저장을 포함한 rollout: **234.25초**.
- CPU 경로 계산 서비스: 4.88초, 4 workers. 물리 실행과 일부 겹치므로 합산하지 않는다.
- 공유 물리 3,199 step: 153.61초; 실행 제어·접촉/상태 평가: 66.18초.
- 8개 모두 IK/관절 제한/자가충돌 검사 통과, 진입 waypoint 도달.
- 6개: 과도 변위로 중단. 2개: 계획된 상승과 마지막 1초 유지까지 완료했지만 꼭지 걸림 실패.
- **candidate_00005: 목표 열매 중심 진입 조건 1.87초 달성**, 완전한 걸림은 아님.
  다른 꼭지(Tomato_07)에 먼저 접촉했고 목표 열매 최대 19.81mm, 주줄기 24.02mm 이동했다.
  목표 과실 20mm 중단 기준에 가까우므로 이 후보를 곧바로 좋은 수확 동작으로 확정하지 않는다.
- 완전한 꼭지 걸림: 0개. 부분 진입은 이번에는 GT 수치 판정이며 새 동작 영상 재생 검증은 아직 하지 않았다.

마지막 그래프가 기존 변수 `azimuth_deg`를 기대해 KeyError가 났다. 이때 이미 8개 물리
결과/trace/CSV가 완전 저장돼 있었다. 새 6D 그래프를 지원하도록 고치고 **물리를 다시
실행하지 않고** 그래프만 생성했다. 원래 오류/종료 코드는 보존했으며
`postprocess_recovery.json`에 후처리 복구를 기록했다.

## 시간 예상과 실행 단위

동일 4환경과 이번 8개의 완료/조기중단 비율을 가정한 단순 외삽이다.
영상 생성은 제외하며, 환경 수가 달라지면 이 값을 그대로 사용할 수 없다.

| 후보 수 | 예상 시간 |
|---:|---:|
| 32 | 약 16분 |
| 64 | 약 32분 |
| 128 | 약 63분 |
| 256 | 약 2시간 6분 |
| 2,048 | 약 16시간 40분 |

따라서 우선 **64개 정도를 실행하고 실패/부분 진입을 검토**하는 편이 적절하다.
나눠 실행하는 것 자체가 처리 속도를 올리지는 않는다. 좋지 않은 탐색 범위에서 오래
계산하는 것을 피하려는 목적이다. 성공 후보가 많아져 끝까지 실행하는 비율이 올라가면
더 오래 걸릴 수 있다. 반대로 현재 소규모 시험의 마지막 빈 슬롯 영향도 있다
(active env-step fraction 0.791). 통계적 신뢰구간을 산출할 표본 수는 아니다.
16/32/64환경 처리량은 이 새 경로로 아직 측정하지 않았다.

## 동작과 부분 성공 정의

기존 기본 동작은 유지하고 `--trajectory-mode staged6d`를 선택할 때만 적용한다.
별도 고리 fixture가 아닌 **실제 로봇과 그리퍼 전체**가 움직인다.

- 초기 로봇 상태는 기존 공통 관찰 자세이며, 준비 waypoint까지도 물리로 이동한다.
- 준비 waypoint: 목표 중심에서 수평 바깥으로 170mm 떨어진 곳.
- 진입 waypoint: 고리 전체가 과실 충돌 구 아래에 있고, 옆으로도 떨어진 곳.
- 삽입: 고리를 수평으로 안쪽으로 이동.
- 상승: 수직 또는 앞뒤로 기울어진 직선으로 이동.
- 마지막 1초 유지. 접촉만으로 상승 도중 멈추던 기존 guard는 이 모드에서 적용하지 않는다.
- 과도 변위/위험 접촉/파손 중단은 유지한다. 당김은 아직 지원하지 않는다.

| Sobol 변수 | 범위 |
|---|---:|
| 접근 방위각 | -35~+35도 |
| 과실 충돌 구 바닥 아래 wire 표면 여유 | 5~15mm |
| 좌우 offset | -8~+8mm |
| 수평 삽입 거리 | 25~60mm |
| 상승 전진각 (양수=안쪽) | -15~+15도 |
| 상승 경로 길이 | 20~45mm |

고리 roll/elevation은 0으로 고정했다. CAD 고리 원점/축을 그대로 사용한다:
+X는 열린 쪽/로봇 방향, +Y는 고리 평면 법선(여기서는 아래), +Z는 좌우 방향.
원래 타겟 충돌 반지름은 10.525mm다. 형상 바닥은 현재 물리 collider의 구로 정의했다.

현재 속도는 기존 접근 35mm/s, 상승 2mm/s 상한과 smoothstep 시간 배분을 유지한다.
물리 timestep은 practical60 (60Hz, armature 5e-4, PGS 64/4). 실행 속도를 높이려고
로봇 동작 속도나 파손 임계값을 바꾸지 않았다.

부분 중심 진입은 실제 target centre를 고리 좌표계로 바꿔, 중심이 뒤쪽 반원 영역에
있고 과실 단면이 원형 내부 여유에 들어오며 고리 평면에서 2mm 이내인 경우다.
초기에는 영역 밖이어야 하고 insert/rise/hold 단계만 인정한다. 단순 거리나 접촉 여부만
사용하지 않는다. `center_entry_safe`는 그 순간 정한 변위/접촉 한계 등을 통과했다는
뜻이며 실물 안전 인증이 아니다. 최종 miss/실패와 부분 진입 기록은 독립적이다.

`under_center_alignment`는 저장한 trace에서 별도로 계산한 아래쪽 평면의 2D 투영 정렬이다.
실제 고리 평면에 중심이 진입한 것과 구분한다.

```bash
./nvidia-sim/run_gpu_candidate_dataset.sh \
  --trajectory-mode staged6d --physics-preset practical60 \
  --num-envs 4 --candidates 8 --planning-workers 4 --schedule continuous
```

실행 폴더: `runs/20260921_170634_staged6d_timing_pilot/env4_n8_final/`.
상위 폴더의 `pilot_report.json`, `pilot_results.csv`에 시간 예상·부분 진입 분석을 저장했다.
CSV는 Excel용 UTF-8 BOM으로 저장했다. `validation/trajectory_pilot.json`에도 요약을 보존했다.
앞선 `env4_n8`, `env4_n8_repeat`는 사용자 입력 중단 시 프로세스가 종료된 불완전 실행이다.
완성된 샘플과 섞지 않는다. 새 테스트/코드는 미커밋 상태다.
