## 영역 수확 규칙과 초기 구현 이력

영역 수확 판정 규칙은 현재도 유지한다. 아래의 관절 보존/후보 검사/자산 경로는 대기 시간 최적화 전 구현 이력이며, 현재 기본 실행은 문서 맨 위 절을 따른다. 사용자가 열매까지 충돌을 끄고, 그리퍼가 원하는 위치에 들어가면 그 영역의 열매를 모두 수확한 것으로 처리하도록 변경했다.

- 준비된 식물에서 가장 두꺼운 `Stem_MainStem_*`만 식물 장애물로 남긴다. 열매·송이 중심가지·꼭지가지·가는 가지는 `contype=conaffinity=0`으로 실제 물리 충돌을 제거한다. 시각적 농장과 카메라 가림은 유지한다.
- 로봇 자체와 거터 등 구조물의 충돌은 유지한다. 동일한 새 모델로 준비·삽입·후퇴 전체 경로를 검사한다. 원래 방향이 주줄기에 막히면 같은 카메라 관측에서 yaw 0/-25/+25/-50/+50도를 검토하고, 각 방향마다 기존 준비 연결 방식 최대 3개를 사용한다. 진입 깊이는 기존 계획기의 최소값인 선단 뒤 15mm이며, 집단 선정도 수확 판정과 동일하게 과실 중심의 영역 포함 여부를 사용한다.
- 그리퍼는 열린 채로 진입하고 0.3초 정지한 뒤 기존 경로로 후퇴한다. 벨트·닫기 반복과 힘에 따른 실제 꼭지 분리는 이 모드의 수확 조건에서 제외한다. 물리 분리 콜백은 비활성화하지만 관절·질량·스프링·마찰·접촉 한계를 임의로 바꾸지 않는다.
- 저장된 실제 `Tool_fixed` 자세가 계획 자세에 도달했는지 확인한다(위치 오차 5mm 이하, 자세 오차 3도 이하). 도달한 실제 자세에서 과실 **중심**이 tool 좌표 `x=[-48,48]mm, y=[0,158]mm, z=[13,61]mm` 안이면 일괄 수확 처리한다. 경로를 지나가는 중의 과실은 집계하지 않는다.
- 집계에는 준비된 모든 식물의 해당 영역 내 열매를 포함하며 색상은 제한하지 않는다. 다음 목표를 정할 때는 기존처럼 카메라에서 보이는 익음 proxy 집단을 사용한다. 숨겨진 과실 위치를 목표 생성에 사용하지 않는다. 수확 결과를 계산할 때만 SIM-GT 실제 위치를 사용한다.
- 수확 원장은 `assumed_harvest_*`와 `geometric_capture.json`에 저장한다. 실제 분리 이력과 구분하고 중복 집계를 막는다. 수확된 열매는 3D 뷰어에서 숨기고, 다음 GPU 카메라 레이트레이싱 전에 렌더 전용 위치를 옮겨 RGB/깊이/GT와 가림에서 함께 제거한다. 물리 상태를 순간 이동시키는 방식이 아니다.
- `prepare-patrol`의 새 기본 모드다. 기존 자산은 `prepare-geometric-patrol SOURCE_ASSETS NEW_ASSETS`로 복제 변환할 수 있다. 원본과 과거 결과는 보존한다. 모든 결과는 `training_eligible=false`, `harvest_success=null`이며 실제 분리·포집 검증 자료로 집계하지 않는다.

아래의 접촉/분리 수치와 실패 사례는 이 변경 전 시험 이력이다.

## 판단과 재사용 범위

- 기존 `CameraPatrol`이 관측된 익은 열매가 최소 2개인 왼쪽 베드 집단을 대기열에 넣는다. 식물의 숨은 과실 중심을 관측값으로 사용하지 않는다.
- 카메라의 가려지지 않은 RGB/optical-Z depth/instance ID로 기존 `CameraRegionSelector`의 집단·방향·조준점을 만든다. 색상/익음은 SIM-GT 라벨이다. 영상 인식기를 학습한 결과는 아니다.
- 기존 `plan_adapter`와 `motion_kinematics`로 리프트·팔·그리퍼 명령을 생성한다. 수평 준비 경로, 높이·이동 동시 준비 경로, 관절 준비 경로 순으로 최대 세 개만 검토한다.
- 준비 구간을 같은 native collision model에서 검사한다. 로봇 자기충돌/고정 구조물 교차는 차단한다. 고정해 놓은 탄성 가지의 기하 겹침은 진단값으로 남기고, 실제 변형 후 관통 여부는 기존 GPU 물리 판정이 결정한다.
- 현재의 열기 → 진입 → 양쪽 벨트 안쪽 회전·닫기/열기 반복 → 후퇴를 그대로 사용한다. 관통 한계는 일반 1mm, 기존 지정된 벨트/대상 접촉 구간만 2mm이다. 물성·분리 조건을 성공에 맞춰 바꾸지 않았다.
- 실패한 준비 경로는 제한된 추가 관측 위치에서 다시 검토한다. 소진 결과는 `finite_*`/unknown으로 기록한다. 실제 물리 무효 상태는 그대로 다음 수확에 사용하지 않고 전체 순회를 중단한다.
- `newton_active_window`/`newton_window_continuation`이 관절 위치·속도, 분리 이력, equality, damping, warmstart, 물리 시간을 검증하고 이어간다. 매 이동/수확 때 과실을 복구하거나 환경을 초기화하지 않는다.
- 같은 물리 모델은 GPU 엔진을 재사용한다. 파생 계산 버퍼만 새 실행과 동일하게 정리한 뒤 검증된 측정 상태를 다시 설정한다. 모델이 달라지면 새 엔진을 만든다.

## 실행 자산과 범위

`prepare_newton_patrol.py`가 원본 농장 USD와 기존 S300/RB5/그리퍼 변환기로 자산을 준비한다. 전체 농장 시각 배경은 유지한다. 이번에 준비한 식물은 **각 식물의 모든 송이**를 포함한다. 활성 식물의 줄기·송이는 탄성, 나머지 준비된 식물은 같은 위치의 고정 충돌체이며 이미 분리된 과실은 계속 동적이다. 준비 범위 밖 농장의 식물은 시각 배경이다. 잎은 기존 정책대로 충돌하지 않는다.

따라서 과거의 송이 하나/133 DOF 실행과 이번 한 그루의 세 송이/355 DOF 실행의 속도를 동일 작업량 비교로 해석하면 안 된다. 미리 지정한 경로 끝은 실험 예산이며 실제 레일 전체 길이 또는 수확 가능 범위를 의미하지 않는다.

```bash
./nvidia-sim/run_s300_newton.sh prepare-patrol /root/farmily_runtime/newton/assets/patrol_longer --end-station 1.5
./nvidia-sim/run_s300_newton.sh camera-patrol /root/farmily_runtime/newton/assets/patrol_longer --max-harvests 6
```

## 확인한 결과

1. `patrol_entry_v3_smoke`: 입구 → 0.15 → 0.30 → 0.45m를 실제 GPU로 이동했다. 0.15/0.30m에서 각각 관측된 익은 열매 9/13개가 판단에 들어갔다. 최초 관절 준비 경로는 그리퍼 고정부와 송이 peduncle 접촉으로 중단됐다. 이 실패 결과도 보존했다.
2. `patrol_resident_movement`: 위 네 구간을 엔진 재사용으로 새로 실행했다. **저장된 모든 스텝의 qpos/qvel/자세/명령/분리 상태/시간이 개별 프로세스 실행과 정확히 일치**했다.
3. `patrol_cartesian_suffix_v2`: 같은 측정 시작 상태에서 기존 수평 준비 경로를 실행했다. **44.061초 동작 완주, 열매 3개 분리, 최대 활성 관통 0.905mm**였다. 분리는 준비 중 1개, 닫는 중 1개, 후퇴 중 1개였다. 이를 벨트만으로 세 개를 땄다거나 회수까지 완료했다고 해석하지 않는다.
4. `patrol_entry_loop_gui`: 실제 브라우저 시작 버튼으로 실행했다. 입구 전진 → 위 수확 → 재관측 → 추가 5cm 이동을 마쳤고 지정된 0.5m 시험 끝에서 종료했다. 수확 구간의 **모든 저장 상태는 3번 headless 실행과 정확히 일치**했다. 브라우저 오류 0개. 다음 준비 경로의 자기충돌 및 IK 미발견도 기록됐다.

위 시험의 카메라는 240×320이다. 3번의 물리 루프 RTF는 약 1.00, GUI 전체 순회의 물리 시간은 59.252초, 구간 준비·검증·계획 등을 포함한 벽시계 시간은 269.432초였다. 별도 자산 변환도 병행한 실행이므로 전용 성능 비교값은 아니다. **전체 순회가 실시간이라고 주장하지 않는다.** 현재 큰 지연은 매 구간 자산 준비·검증 및 계획 전환에 남아 있다.

## 추가 반복 및 여러 식물 연결 시험

`patrol_entry_loop_final`에서는 재관측 후 두 번째 동작을 실제로 실행했다. 첫 경로는 자기충돌 검사에서 거절됐고, 기존 동시 높이/이동 준비 경로로 전환했다. 첫 수확은 완주했으며 두 번째는 `return_ready`에서 그리퍼 오른쪽과 Truss_01 peduncle가 1.456mm 겹쳐 중단됐다. 두 번째 구간에서 추가 분리 3개가 관측됐지만 물리 실패 구간의 결과로 보존하며 성공으로 집계하지 않는다. 이 시험에서 동일 MJB/XML 공유로 약 2.7GiB 중복 저장을 피했다.

세 그루(Plant_17/18/19, 총 9송이·90열매)와 0..0.85m 경로의 자산도 새로 생성했다. 원본 자산 생성기/변환기를 재사용하며 `--allow-multiple-windows`로 기존 명시적 다중 식물 지원을 사용한다. 새 GPU 세그먼트 메타데이터가 바뀌는 경우 정적 CONNECT 호환 목록을 동일 실행 재사용으로 잘못 취급하던 연결 오류를 수정했다. 이전 원본 GPU 목록과 모델이 변조되지 않았음을 확인한 뒤 목록을 복원하고, 새 세그먼트의 정확한 동결 대상 검사를 다시 수행한다. 충돌체나 동적 제약을 삭제하지 않는다. 해당 복원/변조 거절 회귀시험도 추가했다.

## 저장 자료와 한계

각 `step_*`에는 의사결정, 카메라 `rgb.png`/`recognition.png`/`rgbd_gt.npz`/관측 JSON, 준비 경로 대안과 거절 이유, 물리 `summary.json`/실제 `states.npz`/분리 이력이 있다. 최상위 `summary.json`/`patrol.json`은 전체 순회와 남은 대상을 기록한다. 같은 바이트의 큰 MJB/XML은 SHA 검증 후 해당 실행 안에서 공유해 중복 저장을 줄였다.

- 실제 카메라 노이즈, 검출기, ROS2는 이번 범위가 아니다.
- 카메라 목표 생성은 가시 픽셀만 쓰지만 IK/충돌 검사에는 알려진 시뮬레이터 모델을 사용한다.
- 순회 실행기 구현과 모든 송이의 완전 수확은 서로 다르다. 준비 경로 실패, 관측 부족, 예산 종료를 분리해서 읽어야 한다.
- 분리 과실의 실제 수거는 검증하지 않았다. `training_eligible=false`, `harvest_success=null`을 유지한다.
- 기존 단일 수확/표시 기능 및 원본 실패 결과는 보존했다. 현재 작업 브랜치는 `codex/s300-newton-standalone-20261108`이다.
