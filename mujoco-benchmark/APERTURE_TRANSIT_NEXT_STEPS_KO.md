# 과실 통과 좌표와 꼭지 안착 좌표를 분리하는 다음 실험

기준: `dc01b3bd83e8fdf98cf2f097a767580b427bd9a5`.
작업 브랜치: `codex/aperture-transit-20260927`.
검증한 제안기 코드: `343573c0c6ef229f91b0c10cb6fc5930d8cb7f04`.

## 1. 근거와 해석 범위

다음을 대조했다.

- `HOOK_SEATING_SERVER_RESULTS_KO.md`
- `validation/hook_seating_server_20260927/inputs/robot_under/candidates.json`
- 같은 입력 디렉터리의 `planning_inputs.json`
- `seating_goals.json`, `endpoint_results.json`
- `nvidia-sim/rl/dataset_motion.py`

기존 결과의 분모는 **27개 계획, 새 동작 물리 실행 0개, baseline 물리 실행 1개**다. 정적 끝 자세 5개가 유효한 것은 전체 접근 가능성이나 기계적 유지 성공을 입증하지 않는다. 이번 검토에서 동영상 전 프레임을 독립 검증하거나 서버에 SSH로 접속해 새 물리를 돌리지는 않았다.

`seating_00_under`는 최종 안착 위치의 XY를 고정한 채 세계 Z로 40mm 올라간다. 끝 자세에서 과실 중심의 RING 좌표는 약 `[-20.9968, 16.2516, 6.0567]mm`이고, 고리 평면 투영 오프셋은 **21.8529mm**다. 입력 과실 경계구 반지름은 **13.9096mm**다.

반지름 27.5mm, 와이어 반지름 1mm인 이상적인 원 안쪽으로 경계구 전체를 통과시킬 때 중앙 통과 여유는 약 **12.5904mm**다. 32분절 현으로 계산하면 약 **12.5573mm**다. 이는 열린 반원의 모든 진입에 적용하는 필요조건이 아니라 중앙 통과 경로를 만드는 보수적인 조건이다.

따라서 **과실이 고리 평면을 통과할 때의 좌표**와 **과실 어깨 위에서 꼭지를 안착시킬 때의 좌표**를 분리해야 한다. 끝 자세가 유효하다는 이유로 그 XY를 아래부터 유지하면 안 된다.

독립적인 32캡슐 반원과 입력 경계구로 국소 경유점 구간을 표본 계산한 결과는 다음과 같다.

| 단순 기하 비교 | 표본 최소 간격 |
|---|---:|
| 기존 XY 고정 수직 상승 | 약 -9.282mm |
| 중심 정렬 상승 후 위쪽 옆 이동 | 약 +2.289mm |

이 표는 실제 온실·팔·마운트·다른 과실의 충돌 검사나 물리 결과가 아니다. 경계구의 겹침 크기를 실제 과실 mesh의 침투량으로 해석하지 않는다. 양의 간격도 관절 추종 오차나 식물 변형을 보장하지 않는다.

## 2. 첫 번째로 시험할 연결

기존 정상 시작과 `preapproach/approach` 경유점은 유지한다.

1. 과실 아래에서 고리 중심의 평면 투영을 과실 중심에 맞춘다.
2. 기울기 변경이 필요하면 아직 아래에서 과실 중심을 기준으로 회전한다. RING 위치를 `p = c - R * c_local`로 함께 변경한다.
3. 과실 중심이 고리 안쪽 중앙을 지나는 상태로 고리 법선 방향으로 올린다.
4. 고리 평면이 과실 어깨를 지난 다음 원래 꼭지 안착 위치로 옆 이동한다.
5. 필요한 경우에만 짧은 법선 방향 정렬을 추가한다.

`seating_00`의 기하 예시는 다음과 같다. 단위는 world m이며 회전은 기존 quaternion이다.

```text
중심 아래: [-0.696152523661374, 0.9158217278439791, 0.4534833653902833]
중심 위:   [-0.696152523661374, 0.9158217278439791, 0.4934833653902833]
원래 안착: [-0.7022053187722946, 0.8948237864349288, 0.4934833653902833]
```

첫 비교는 roll/pitch를 추가하지 않은 0번 목표부터 한다. 목표와 회전을 유지하고 연결 방식만 비교할 수 있다. 더 많은 회전 자유도가 반드시 필요하다고 가정하지 않는다.

회전할 때는 과실 중심과 RING 중심, Hook 바디 원점을 혼동하지 않는다. Hook 원점은 `p_hook = p_ring - R * RING_OFFSET`다. 과실을 피하는 회전이어도 마운트와 팔은 크게 움직일 수 있으므로 전체 로봇 검사는 필요하다.

## 3. 추가한 제안기 사용법

`propose_aperture_transit.py`는 기존 one-insert/one-seat 진단 후보만 변환한다. 새 엔진이나 실행기를 만들지 않는다. 기존 진단 경유점 스키마와 16개 상한을 지킨다. 원본 prefix와 hold/verify suffix는 보존한다.

**원본 verify는 작은 기존 경유점일 뿐 부하 검증이 아니다.** 출력에도 `source_verify_is_not_load_validation=true`를 기록한다. 이 제안기가 실제 접촉·유지 양성 대조를 대신하는 것은 아니다.

실제 32개 와이어에서 RING 중심부터 각 와이어 표면까지의 최소 거리를 계산해 `aperture-inradius-m`에 넣는다. 과실 경계구가 실제 collision mesh를 포함하는지도 확인한다. 아래 `0.02646m`는 현재 명목 반원의 보수적인 근사치이며 서버 자산 확인을 대신하지 않는다. `plane-buffer`는 계획용 간격이지 물성 변경 옵션이 아니다.

```bash
V=mujoco-benchmark/validation/hook_seating_server_20260927/inputs/robot_under
OUT=/root/docker_share/mujoko_debugging_data/NEW_aperture_proposals
python mujoco-benchmark/scripts/propose_aperture_transit.py \
  --source-candidates "$V/candidates.json" \
  --planning-inputs "$V/planning_inputs.json" \
  --candidate seating_00_under \
  --wire-radius-m 0.001 --aperture-inradius-m 0.02646 \
  --plane-buffer-m 0.001 --output "$OUT"
```

`candidates.json`과 `proposal_report.json`만 만든다. replay assets나 실행 trace는 만들지 않는다. 모델·초기 상태·해시를 대조한 새 실행 폴더에서 기존 자산을 읽기 전용으로 재사용하고, 기존 `plan_candidates.py`로 계획한다. 생성된 **관절 명령 배열 전체**를 native preflight로 검사한다. 원하는 Cartesian 경로와 관절 보간 후 경로가 정확히 같다고 가정하지 않는다.

새 `seat` 단계는 기존 planner의 rise 전용 2mm/s 분기가 아니라 기본 35mm/s 분기로 들어갈 수 있다. 제안기는 `minimum_seconds`를 명시해 최종 옆 안착 이동을 명목 cubic 속도 2mm/s 이하로 제한한다. 통과 이동은 명목 10mm/s를 사용하며 생산 속도 설정은 바꾸지 않는다. 10초 경유점 상한을 넘는 이동은 분할한다. 실제 TCP와 관절의 속도·가속도는 다시 검사해야 한다.

## 4. 목표 생성 단계에 추가할 접근성 조건

목표 꼭지와 뒤쪽 16개 와이어의 끝 자세만 보지 말고 전체 32개 와이어, 마운트, 팔과 환경을 검사한다. 각 목표에 **통과용 중심 정렬 상태 또는 열린 입구로 빠져나가는 상태까지의 짧은 연결 증거**를 붙인다. 단순 IK 성공은 연결 성공이 아니다.

단계별 과실–고리 상대 좌표, 최소 여유, IK branch와 전체 trace 검사 결과를 보존한다. 구형 경계는 보수적인 계획용 근사이므로 그 검사에서 탈락했다고 실제 수확 불가능으로 라벨링하지 않는다. 목표 기하 검사와 실제 부하 상태의 동역학 검증도 분리한다.

중심 통과 방식이 비목표 구조에 막힐 때만 두 번째 경로군을 시도한다. 정적 안착 자세에서 고리를 local **-X**로 이동해 목표 꼭지가 **+X 열린 쪽**으로 빠져나가는 연결을 역으로 검사한다. 목표 캡슐 전체가 실제 입구 바깥에 오는 거리를 계산하되 와이어·과실·마운트·팔 충돌을 모두 확인한다. 이를 정상 시작에 연결해 앞으로 실행한다. 접촉한 식물의 동역학을 거꾸로 재생하는 방식은 아니다. 이 두 번째 경로군은 이번 코드에 구현하지 않았다.

## 5. 접촉·유지 양성 대조

무부하 정적 fixture의 힘이 작다는 이유만으로 그 기하 배치를 실패라고 볼 수는 없다. 반대로 가까이 배치한 것만으로 실제 포획이라고 볼 수도 없다.

같은 모델·물성·제어기에서 이미 안착한 시작 자세를 쓰는 **부하 대조 시험**을 별도로 만든다. 선택 와이어에서 목표 꼭지 쪽을 향하는 공통 법선 방향으로 작은 이동을 주고 정체성, 실제 이동, 접촉력, 상대 자세를 함께 측정한다. 변위 상한은 0.5mm와 1.0mm의 두 경우로 미리 제한하고 물리 유효성이나 비목표 힘 조건을 위반하면 중단한다. 이 실험은 정상 시작 자동 진입 성공에 포함하지 않는다. 실제 이동이 추종 오차에 묻히면 부하 시험 자체가 성립하지 않았다고 기록한다.

음성 대조는 같은 시간·제어 조건에서 열린 쪽으로 벗어나는 자세, 과실 중심만 들어온 자세 또는 다른 꼭지 접촉으로 구성한다. 무부하 정지, 부하 유지, 부하 해제 후 이탈을 구분한다. `initially_seated=true`를 false로 바꾸어 기존 판정기를 통과시키지 않는다.

정상 시작 동작의 유지 증거에는 다음이 함께 있어야 한다.

- 외부 초기 상태에서 목표 꼭지가 유효 공간으로 들어오는 시간 이력.
- 정확한 목표 꼭지와 뒤쪽 와이어의 안쪽 안착 및 의도된 접촉.
- 선언한 방향으로 실제 부하·변위를 주는 동안 유지되는 목표 정체성과 안착.
- 연속 timestamp의 hold 1초와 별도 verify 구간.
- 전 로봇의 비허용 힘, 잘못된 꼭지, 침투, 추종 오차 검사.

기존 보고 문턱 0.01N과 물리 유효성 기준 0.5mm를 바꾸지 않는다. 0.01N은 실물 손상 한계나 무접촉 인증값이 아니다. 정적 후보의 비관통 조건과 동역학 관통 유효성은 별도로 출력한다.

열린 반원은 모든 방향의 이탈을 막는 cage가 아니다. 한 방향 부하를 버틴 결과를 모든 방향 유지나 파단 수확 성공으로 해석하지 않는다. 실제 수확 당김 방향이 접촉 법선과 다르면 그 방향도 검증해야 한다.

## 6. 이번 한 라운드 예산

| 구분 | 상한 |
|---|---:|
| 유효 끝 자세 5개에 대한 중심 통과 계획 | 5개 |
| 필요한 경우 열린 입구 역연결 | 추가 5개 |
| 좌표·IK 연결 수정 재시험 | 추가 2개 |
| 정상 시작 새 동작의 물리 실행 | 6회 |
| 부하 양성·음성 fixture 물리 실행 | 별도 4회 |

우선 `seating_00_under` 한 개부터 검사한다. 같은 실패 방식을 각도만 바꾸며 반복하지 않는다. 기존 7경로 진단이나 불필요한 baseline 물리 재실행은 하지 않는다.

정상 시작 성공을 확인한 경우에만 남은 6회 예산 안에서 재현과 작은 위치·자세 교란을 시험한다. 금지 충돌 경로를 강제 실행하지 않는다. 목표 접촉은 기존 정확한 쌍과 단계의 진단 정책 안에서만 다룬다.

모든 계획이 실패하면 가장 긴 유효 prefix와 다음에 막힌 쌍·단계를 보고하고 라운드를 끝낸다. 이를 물리적 불가능의 증명으로 쓰지 않는다.

최종 보고에는 branch/HEAD/해시, 제안·계획·물리 실행·대조 실행의 분모, 최소 거리, 비허용 힘, 실제 이동, 실패 단계와 대표 MP4를 넣는다. 명목 경로 영상과 새 물리 실행 영상을 구분한다. SIM-GT 교사 탐색을 RGB-D 학생의 성능으로 집계하지 않는다. 수동 라벨링이나 실물 꼭지 GT 요구를 추가하지 않는다.

## 7. 이번 코드 검증 범위

로컬 NumPy/SciPy에서 **20개 테스트 통과**. 동일 코드의 [GitHub Actions 36327879185](https://github.com/hjpark-rdv/tomato_robot_sim/actions/runs/36327879185)도 Python 3.11.16에서 **20개 통과, skip 없음**이며 compileall을 통과했다.

이는 순수 기하·스키마·좌표·원본 보존·출력 검사다. MuJoCo 물리 실행이나 실제 온실 전체의 native 검사로 보고하지 않는다. 이번 코드에서는 생산 planner, 물성, 평가기, 운영 정책을 변경하지 않았다. 다음 서버 작업은 이 제안기를 실제 IK·전 경로 검사·물리 실행에 연결하는 것이다.
