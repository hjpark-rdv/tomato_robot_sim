# GPT-6 Pro 논의용: 복잡한 토마토 하우스에서 비목표 장애물을 건드리지 않는 수확 접근

작성: 2026-09-27 KST. 저장소 `/root/farmily_tomato`, 브랜치 `mjlab-performance`.
확인한 HEAD: `13314cd`. 이후 주변 식물 탄성 비용 진단 스크립트와 관련 문서는 작업 트리에 있으며 아직 커밋하지 않았다.
이 문서는 구현 완료 보고와 후속 설계 논의를 구분한다. 아래 제안은 아직 구현하지 않았다.

## 1. 사용자 목적과 논의 요청

사용자는 로봇에 가까운 쪽 토마토를 대상으로, **타깃이 보이는 RGB-D 사진 한 장 → 모델이 진입각 한 개 예측 → 고리형 도구로 접근**하는 시스템을 원한다. 주변 토마토·주줄기·거터를 뚫거나 밀어서 접근하는 것은 목적에 맞지 않는다.

핵심 질문은 다음과 같다.

> 기존 사진 기반 직접 각도 예측과 MuJoCo 실행 구조를 최대한 재사용하면서, 비목표 충돌체에 접촉하지 않는 접근·진입·상승·복귀를 어떻게 구현하고 검증해야 하는가? 시뮬레이션 처리 속도를 유지하려면 어떤 물리 표현과 계획/감시 구조가 적절한가?

여기서 ‘모든 충돌체와 무접촉’이라고 하면 수확에 필요한 타깃 꼭지 접촉까지 금지하므로 모순이다. **비목표 물체와의 접촉 금지**와 **도구–타깃의 의도된 접촉 허용**을 구분해야 한다. 정확한 허용 접촉 목록과 허용 단계는 아직 확정되지 않았다. 같은 송이의 다른 열매도 비목표다. 타깃 주줄기가 탄성이라는 이유로 밀어도 된다는 뜻은 아니다.

사용자가 이전에 말한 ‘유체’는 이 문맥에서 유체역학이 아니라, 줄기와 송이가 휘고 밀리는 **탄성 관절 모델**을 뜻한다. MuJoCo에서는 강체 분절을 관절로 연결해 이를 표현한다.

## 2. 유지해야 할 요구사항

- 기존 데이터 수집, GLB 변환, RGB-D, IK, 물리 실행, 결과 저장·재생 코드를 재사용한다. 별도 중복 파이프라인을 만들지 않는다.
- 테스트 중 여러 랜덤 각도를 물리로 시도해 성공하는 것을 고르는 방식으로 되돌아가지 않는다.
- 신경망 직접 예측 각도와 계획기가 보정한 각도를 혼동하지 않는다. 보정을 도입한다면 각각 저장하고 사용자에게 동작 변경을 설명해야 한다.
- 모든 타깃에 성공 경로가 존재한다고 가정하지 않는다. 가림·도달 불가·주변 장애물 때문에 시도를 보류할 수 있다.
- 탐색 실패만으로 물리적으로 수확 불가능하다고 단정하지 않는다.
- 현재 중심 진입 라벨을 완전한 고리걸기·파단·수확 성공으로 바꾸지 않는다.
- 충돌을 없애거나 관통 허용치를 키워 시험을 통과시키지 않는다.
- 성능은 화면을 끈 조건이 우선이다. 처음에는 소규모로 검증한다.

## 3. 현재 장면과 물리 범위

| 구성 | 현재 운영 장면 | 유의점 |
|---|---|---|
| 로봇 | 팔 6관절 + 리프트, 동적 관절 제어 | 도구뿐 아니라 팔 전체가 장애물을 피해야 함 |
| 원래 타깃 줄기·송이 | 탄성 관절 모델 | 원래 타깃 열매 10개, Tomato_06 제외 |
| 주줄기 외형 | 기존 줄기와 새 v9 GLB 외형을 혼합 | 두 외형이 같은 주줄기 충돌 골격을 공유 |
| 주변 식물 | 68개, 거터 양쪽에 반대 방향으로 배치 | 타깃 적격은 통로/로봇 쪽 뿌리 위치로 구분 |
| 주변 주줄기 충돌 | 16분절 × 68개 = 고정 캡슐 1,088개 | 부딪혀도 주변 줄기는 밀리지 않음 |
| 주변 송이 | 조밀 배치 총 106개, 운영 장면에서는 시각 전용 | 전체 주변 열매·송이 충돌 연결은 아직 안 됨 |
| 거터 | 원본 USD 판·테두리·받침리브 18개 고정 충돌체 | 열린 홈 유지. 지지 다리·철사·배지까지 모두 충돌 처리한 것은 아님 |
| 주변 잎 | 시각 전용 | 잎을 건드리지 않는 조건은 현재 검증할 수 없음 |

GLB 송이는 기존 보정 규칙과 크기 배율 0.5를 사용한다. 송이 배치용 Y 회전과 로봇 진입 방위각은 서로 다른 변수다. 현재 물리 타깃으로 실행 가능한 것은 원래 송이의 10개 열매이며, 주변 시각 송이로 타깃을 전환하는 기능은 아직 없다.

주변 송이까지 충돌/탄성으로 만든 것은 최근 **별도 진단 모델**뿐이다. 운영 모델 전체에 적용한 것으로 이해하면 안 된다.

## 4. 현재 사진 → 실행 흐름

1. 대상별 초기 장면을 설정한다.
2. 가상 카메라의 nominal RGB-D 1 view를 촬영한다. local/context crop과 depth 특징을 사용한다.
3. 사진이 가려졌거나 crop이 사용 불가능하면 `no_usable_observation`으로 미시도한다.
4. 기존 ResNet18/DINOv2 특징 + 회귀 모델로 월드 진입 방위각 1개를 예측한다.
5. 기존 staged6d 경유점 생성기에 이 각도를 넣는다.
6. IK와 관절 제한·속도·자기충돌 검사를 통과하면 실제 MuJoCo 물리를 최대 한 번 실행한다.
7. 결과와 상태 궤적을 저장한다. 타깃마다 초기 상태로 독립 reset한다.

현재는 실제 detector 기반 시스템이 아니다. 타깃 중심/꼭지 기하와 crop 준비 등에 simulator GT를 사용한다. 한 장면에서 열매를 실제로 제거하며 다음 열매를 수확하는 연속 작업도 아니다.

직접 예측 경로의 주요 설정: 준비 거리 170mm, 하부 여유 2mm, 좌우 오프셋 0, 삽입 거리 42.5mm, 최종 상승 32.5mm, `diagonal_75_return` 상승 프로필. 전체 경로를 자유롭게 장애물 사이로 계획하는 구조가 아니다.

각도 학습 라벨은 **측정된 유효 중심 진입 후보 중 타깃 변위가 가장 작은 후보의 각도**다. 유일한 최적각 정답이 아니며, 성공을 발견하지 못한 타깃에는 각도 지도 라벨이 없다. 따라서 현재 회귀 모델에는 ‘안전한 각도가 없음/시도 보류’를 명시적으로 출력하는 기능이 없다.

## 5. 현재 충돌 처리의 결정적 부족

### 5.1 사전 계획

`dataset_motion.plan()`은 경유점 기반 IK를 만든 뒤 관절 제한·속도를 검사하고, 명령 사이를 추가 분할하여 기존 FCL checker의 자기충돌을 검사한다. **새 거터와 주변 식물을 포함한 환경 회피 계획은 연결되지 않았다.** `preflight.passed`가 온실에서 무접촉이라는 뜻이 아니다.

준비 위치까지의 팔 이동, 도구 진입, 상승, 복귀 전체를 검사해야 한다. 도구 끝점 또는 타깃까지의 직선만 안전해도 팔꿈치나 고리 외곽이 장애물에 닿을 수 있다.

### 5.2 실행 중 감시

`RobotEngine.rollout()`은 매 물리 스텝 접촉·관통을 기록한다. 고리, GLB 충돌체, 거터, 주변 주줄기의 침투가 0.5mm를 초과하면 결과를 물리 오류로 분류한다.

그러나 **비목표 접촉 즉시 중단하거나, 최소 거리를 유지하도록 제어 명령을 바꾸지는 않는다.** 현재는 충돌했어도 저장된 위치 명령을 계속 따라가며 밀어붙일 수 있다. 고정 줄기가 움직이지 않고 로봇 관절 추종 오차가 커지는 상황이 실제로 발생했다. 이는 로봇 링크 자체를 탄성체로 모델링했다는 뜻은 아니다.

`invalid_physics` 검사는 사후 물리 품질 검사다. ‘관통 0.5mm 이하’와 ‘비목표 접촉 없음’은 서로 다른 조건이다. 접촉 이벤트가 발생한 뒤 정지하는 것만으로 이미 발생한 접촉을 취소할 수도 없다.

### 5.3 성공 의미

`center_entry_only_v2`는 유효 물리에서 중심 진입 이력이 있으면 `partial_center_entry`로 기록한다. 현재 `center_region()`은 고리 좌표계에서 `x <= -0.001`, `hypot(x,z)+fruit_radius <= RING_RADIUS-WIRE_RADIUS`, `abs(y) <= 0.020`을 검사한다. ±20mm 평면 허용 범위의 **부분 기하 진입**이며 꼭지 포획·파단·수확 완료 판정은 아니다.

비목표 무접촉 성공 지표를 추가하더라도 기존 라벨을 덮어쓰지 말고 별도 필드/평가 기준으로 보존해야 한다.

## 6. 관측된 결과와 한계

### 6.1 복잡한 시각 배경에서 직접 예측

`20260927_dense_house_harvest_test`: 10개 중 중심 진입 6, 미진입 2, 가림 미시도 2. 당시 실행 8개 물리 오류 0. **주변 송이가 시각 전용인 조건**이며 거터·주변 주줄기 충돌을 추가한 뒤의 성능이 아니다.

새 RGB-D에서 예측 각도는 모두 약 -90°로 몰렸다. 복잡한 배경에서의 일반화나 장애물 회피 능력이 입증된 것이 아니다.

### 6.2 주변 주줄기 충돌 추가

동일한 Tomato_01/02/09 저장 경로를 다시 실행한 결과 모두 물리 오류: 최대 주줄기 침투 1.183 / 1.492 / 1.621mm. 원래의 성공 경로도 환경 장애물을 추가하면 안전하지 않다.

### 6.3 화면을 끈 속도

초기 단일 줄기와 현재 고정 주변 주줄기·거터의 동일 3경로, 각 3회 비교: 평균 시뮬레이션 42.25초 처리에 19.387초 → 13.177초. 단, 현재 조건은 모두 물리 오류이며 움직임도 달라졌다. ‘장애물을 늘리면 빨라진다’는 일반 결론이나 정확한 코드 가속률로 해석하지 않는다.

### 6.4 주변 탄성화 진단

기존 타깃은 항상 탄성으로 유지하고 주변만 바꿨다. 240Hz, 화면 없음, 초기 충돌 형상/위치 동일, 각 2회 평균. 모델 생성·촬영·추론·파일 저장 제외.

| 주변 구성 | 고정 실행 시간 | 탄성 실행 시간 | 탄성/고정 |
|---|---:|---:|---:|
| 식물 1 + 송이 1, 로봇 동작 10초 | 3.227초 | 5.029초 | 1.56배 |
| 식물 4 + 송이 4, 로봇 동작 10초 | 3.409초 | 16.708초 | 4.90배 |
| 식물 4 + 송이 4, 로봇 정지 2초 | 0.929초 | 4.006초 | 4.31배 |

동작 시험은 양쪽 모두 관통 기준 실패. 4개 탄성 조건은 최대 침투 8.591mm, 주변 바디 최대 이동 약 309mm로, 정상 물리 응답 검증이 아니다. 정지 시험은 모든 반복에서 최대 침투 약 0.228mm로 기준 통과했다. 전체 DOF는 고정 241, 주변 4개 탄성 1,177이다.

현재 조밀 배치의 식물당 송이 3개를 그대로 탄성화했을 때에는 주변 4개에서 초기 송이끼리 7.645mm 겹침도 발견했다. 고정 물체끼리는 물리 접촉 계산에서 제외될 수 있으므로, 충돌 이벤트가 없다는 사실만으로 초기 배치가 겹치지 않는다고 판정할 수 없다.

**결론 범위:** 타깃만 탄성으로 두는 최적화에는 비용상 근거가 있다. 전체 68개 탄성화, GPU 비교, 실행 중 타깃 전환 비용은 측정하지 않았다. 실시간 전환 기능도 아직 구현하지 않았다.

## 7. 논의할 설계안 — 구현 완료 아님

최소 변경의 출발점으로 다음 구성을 검토하고 싶다.

1. 기존 직접 각도 예측을 유지한다.
2. 운영 물리 장면과 같은 좌표·형상·대상 ID를 쓰는 환경 충돌/거리 조회를 사전 계획에 연결한다.
3. 전체 로봇 경로를 검사하고, 안전하지 않으면 물리 시도 전에 보류한다.
4. 실행 중에는 추종 오차·식물 이동까지 반영해 비목표 거리와 접촉을 감시한다.
5. 타깃 변경은 우선 정지·비접촉·에피소드 경계에서 처리하고, 나머지 식물은 고정 장애물로 둔다.

이 구성은 **위험한 시도 거절**에는 도움이 되지만 **우회 경로 생성**을 자동으로 해결하지 않는다. 다음 정책을 구분해 결정해야 한다.

| 정책 | 예측 각도 처리 | 할 수 있는 일 / 한계 |
|---|---|---|
| 검증 후 보류 | 그대로 유지 | 최소 변경. 현재 고정 경로가 막히면 다른 안전 경로가 있어도 미시도 가능 |
| 각도 고정 + 준비/복귀 경로 계획 | 그대로 유지 | 팔 이동 우회 가능. 삽입·상승 구간 자체가 막히면 해결 못 할 수 있음 |
| 제한적 각도/경로 보정 | 변경 가능 | 예측값을 초기 제안으로 사용. 사용자 의도와 다른 제어 정책이므로 별도 합의·로그 필요 |
| 장애물 인지 모델 재학습 | 모델 변경 | 데이터/실패·보류 라벨 필요. 학습 출력만으로 충돌 안전을 보장했다고 볼 수 없음 |

계획기 내부에서 여러 경로를 기하학적으로 계산하는 것과, 여러 각도를 실제 물리로 시도해 좋은 결과를 고르는 것은 다르다. 다만 내부 계획에서 각도를 수정해도 되는지는 별도로 정해야 한다.

## 8. GPT-6 Pro에 구체적으로 묻고 싶은 사항

1. **접촉 정책:** 도구–타깃 꼭지는 어느 단계에서 허용하고, 타깃 과실·같은 송이 가지·비목표 과실·주줄기·거터·팔 링크는 어떻게 구분할 것인가? 물체 쌍 × 작업 단계별 허용표가 필요한가?
2. **예측과 계획의 역할:** RGB-D 각도 하나를 그대로 실행하되 위험하면 보류하는 것이 첫 단계로 적절한가? 우회 경로 또는 각도 수정은 언제 허용할 것인가?
3. **계획기 연결:** 기존 FCL 자기충돌 검사기에 환경 형상을 추가하는 방법과 MuJoCo 형상을 거리 조회의 기준으로 사용하는 방법 중, 형상 불일치와 유지보수 비용이 적은 것은 무엇인가?
4. **경로 전체 안전:** 단순 이산 검사 사이의 충돌 누락을 어떻게 줄일 것인가? 적응적 세분화·연속 충돌 검사·거리 기반 제한 중 무엇을 우선할 것인가?
5. **안전 여유:** 고리 크기, 깊이 오차, 로봇 추종 오차, 줄기 움직임, 정지 거리 등을 반영한 clearance를 어떻게 정하고 검증할 것인가? 근거 없는 고정 mm 값을 먼저 정하지 않았으면 한다.
6. **실행 감시:** 충돌 후 중단을 넘어서, 비목표 최소 거리가 줄어들 때 감속/정지시키려면 어떤 감시 주기와 기준이 필요한가? 정지나 후퇴 자체의 충돌도 어떻게 검사할 것인가?
7. **가림:** 사진 한 장에서 보이지 않는 장애물은 어떻게 취급할 것인가? GT로 계획을 검증하는 시뮬레이션 단계와 실제 RGB-D만 쓰는 단계를 어떻게 분리할 것인가? 필요 시 추가 관측을 허용할 것인가?
8. **물리 표현:** 비목표를 건드리면 안 되는 작업에서는 비목표 고정 충돌체로 충분한가? 주변 흔들림이 중요한 구간만 탄성화해야 하는가? 고정 모델의 접촉 실패는 실제 식물 반응 평가와 어떻게 구분할 것인가?
9. **타깃 전환:** 미리 준비한 모델을 작업 경계에서 교체하는 방식과 관절 잠금/해제 중 어느 쪽이 적합한가? 잠금만으로 DOF/계산 비용이 줄어든다고 가정하지 않는다. 변형 상태·속도·preload·접촉 상태 이전은 어떻게 처리할 것인가?
10. **실패 표현과 학습:** 안전 경로를 찾지 못함, 인식 불가, 도달 불가, 실제 충돌, 물리 오류를 어떻게 분리할 것인가? 성공 라벨만 있는 현재 각도 회귀에 보류 기능을 어떻게 추가할 것인가?
11. **최종 수확:** 현재 중심 진입까지만 검증된 상태에서 꼭지 걸림·상승·당김·분리·복귀를 어떤 순서로 확장해야 하는가?

원하는 답변은 대규모 재작성 제안보다, **최소 변경 1단계 → 검증 항목 → 필요할 때만 확장할 단계** 순서의 구체적인 설계다. 각 제안이 사진 한 장/각도 한 개/물리 한 번 요구를 유지하는지, 바꾸는지도 명시해 달라.

## 9. 제안하는 작은 검증 세트

아래는 후속 실험 제안이며 아직 실행하지 않았다.

- 장애물 없는 기존 성공 경로: 사전 검사가 정상 경로를 지나치게 거절하지 않는지 확인.
- 거터와 교차하는 경로: 실행 전 거절되는지 확인.
- 고리는 통과하지만 팔꿈치가 줄기에 닿는 경로: 전체 로봇 검사가 잡는지 확인.
- 도구 진입은 가능하지만 상승/복귀 중 다른 열매에 닿는 경로: 단계 전체 검사 확인.
- 타깃 꼭지의 허용 접촉과 같은 송이 비목표 열매의 금지 접촉 구분.
- 초기부터 겹친 고정 식물 배치: 물리 접촉 이벤트에 의존하지 않고 배치 오류 검출.
- 가림/도달 불가/계획 탐색 실패: 보류 사유 저장, 성공률 분모를 숨기지 않음.
- 허용 추종 오차와 센서 오차 범위에서 계획 여유가 유지되는지 확인.

지표는 기존 중심 진입률 외에 비목표 접촉 유무·대상 쌍·단계·최소 거리·관통·추종 오차·보류 사유·계획 시간·물리 실행 시간으로 분리한다. 무접촉 진입과 최종 수확 성공은 별도다.
